# ADR 0017: Personal-Focus Dashboard

Status: Implemented
Date: 2026-06-30
Accepted: 2026-06-30
Decision Source: Dashboard Alignment Review

## Context

Maintley's Dashboard is the primary global action surface. Current product and
UX documentation says the Dashboard should answer:

```text
What needs my attention right now?
```

The current Dashboard already supports several useful behaviors:

- property filtering
- hidden-from-dashboard properties
- role-filtered task visibility
- overdue and due-soon task surfacing
- derived overview metrics

However, the Dashboard also includes score and health language, recent activity
above the task queue, and portfolio-first framing. Those patterns can make the
Dashboard feel like a reporting surface instead of a focused action surface.

Maintley supports different user needs:

- Homeowners may want a simple view of their own property work.
- Family members may care about only one property or the tasks they are helping
  with.
- Owners and managers may sometimes want a full portfolio operations view.
- Owners and managers may also want a quieter personal work view.
- Team members should see work and property context relevant to their role and
  assignments.

## Decision

Maintley's Dashboard will become personal-first and scope-aware.

The Dashboard should prioritize:

- the current user's most relevant work
- overdue and due-soon tasks
- property context needed to act
- one small Maintley Intelligence suggestion when available

The Dashboard may still support portfolio-wide visibility, but portfolio scope
should be a selectable mode rather than the only mental model.

Dashboard scope modes:

```text
My Focus
All Visible Properties
```

Scope should be saved as a user preference rather than an account-wide setting.
This allows one family member, owner, or manager to keep a quiet Dashboard while
another user keeps a broader operations view.

## Implementation Direction

Initial cleanup should:

- remove score and health framing from the Dashboard
- move recent maintenance activity below action-oriented sections
- avoid language such as `Home Health`, `Property Health`, and `portfolio health`
- remove standalone seasonal guidance from the Dashboard while seasonal context
  is folded into Maintley Intelligence
- keep Dashboard data derived from source records
- preserve current property filtering and role filtering

Follow-up implementation should:

- persist the selected Dashboard scope as a user-level preference
- default assigned users toward `My Focus`
- allow owners and managers to choose `All Visible Properties`
- keep the Dashboard Maintley Intelligence consumer under the intelligence layer
- select one direct next action from visible property findings rather than
  creating dashboard-only recommendation rules
- reintroduce seasonal guidance only through the Dashboard Maintley Intelligence
  consumer when it is the most relevant next recommendation

## Reasoning

The personal-first model keeps the Dashboard aligned with Maintley's action
workflow while still supporting portfolio operations.

It reduces noise for users who only need their own work, without removing the
ability for owners and managers to review the broader portfolio.

Using a user preference avoids turning one person's preferred Dashboard into an
account-wide behavior that affects everyone else.

Keeping Maintley Intelligence in the intelligence layer preserves the existing
architecture:

```text
Properties
    -> Maintenance Events
    -> Maintley Intelligence
    -> User Action
```

## Implementation Notes

The first implementation phase removed score and health framing, removed
standalone seasonal tips from the Dashboard, moved recent maintenance activity
below action-oriented sections, and added role-aware Dashboard framing.

The second implementation phase added one direct Dashboard Maintley Intelligence
suggestion generated by the shared intelligence consumer layer.

The third implementation phase added a persisted user-level Dashboard scope
preference:

```text
dashboardPreferences.scope
```

Supported values are:

```text
my_focus
all_visible_properties
```

This preference affects Dashboard presentation only. It does not change account
permissions, property ownership, task assignment, or source records.

The later language-alignment phase replaced the locally calculated Home Health
percentage with category-based Maintley Intelligence readiness from the shared
Intelligence layer. The Dashboard now presents equipment context, maintenance
coverage, and service history as `Starting`, `Building context`, or `Ready`,
with an explanation and next step instead of a property score.

## Alternatives Considered

### Always Portfolio-First

This gives owners and managers maximum visibility, but it creates unnecessary
noise for family members, assigned team members, and owners who want to focus on
their own work.

### Always Personal-First

This simplifies the Dashboard, but it makes portfolio operations harder for
users who actively manage multiple properties.

### Account-Level Dashboard Setting

This is simpler to store, but it applies one user's preference to everyone in
the account. Maintley's role and family/team model needs per-user dashboard
control.

### Keep Score/Health Framing

Scores can look useful, but Maintley Intelligence is documented as guidance,
not grading. Health and score framing risks turning recommendations into an
audit-like judgment instead of practical next steps.

## Consequences

Positive:

- The Dashboard becomes calmer and more useful for individual users.
- Owners and managers keep a path to portfolio-wide visibility.
- Maintley avoids score and health language that conflicts with current UX
  guidance.
- Dashboard recommendations reuse the shared Maintley Intelligence layer.
- User-level scope persistence lets each user choose a quieter or broader
  Dashboard without changing account behavior for others.

Cost:

- Dashboard copy and layout need to adapt by role and selected scope.
- Portfolio-level summary behavior must be carefully derived from visible
  properties rather than duplicated into a new source of truth.

## Non-Goals

- Do not introduce Units or a new organizational hierarchy.
- Do not make the Dashboard a reporting screen.
- Do not create a dashboard-only recommendation engine.
- Do not persist Dashboard summaries as a new source of truth.
- Do not treat Dashboard scope as a permissions model.
