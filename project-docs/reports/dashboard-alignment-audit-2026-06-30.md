# Dashboard Alignment Audit

Date: 2026-06-30

## Purpose

Review the current Dashboard experience against Maintley's documented product direction, UX principles, Maintley Intelligence architecture, mobile guidance, and role/permission model.

This report does not implement changes. It recommends how the Dashboard should evolve before code work begins.

## Current Dashboard Shape

The current Dashboard is structured as:

1. Page header with property filter.
2. Top action section with three cards:
   * Today's Focus
   * Home Overview / Portfolio Overview
   * Home Health Score
3. Recent Maintenance Activity.
4. Needing Attention task queue.
5. Seasonal Maintenance.

Current data behavior:

* Hidden properties are excluded from the Dashboard.
* A selected property can narrow the Dashboard to one property.
* Tasks are filtered through `filterTasksByRole`, so team-scoped users see a narrower task set.
* Tenants are redirected away from the Dashboard to their assigned property route.
* Maintenance history is loaded and aggregated across visible properties.
* Recent activity is derived from maintenance history.
* The Home Health Score is calculated directly in the Dashboard from overdue task count.

## Alignment Summary

The Dashboard is moving in the right direction because it already has:

* A clear action-first card.
* A property scope control.
* Role-filtered task data.
* A focused urgent/due-soon queue.
* Derived metrics rather than persisted dashboard records.

However, it currently conflicts with Maintley's direction in four important ways:

1. The Dashboard still uses score and health language.
2. Recent activity is too prominent for an action-first Dashboard.
3. The Dashboard reads more like a portfolio operations page than a personal daily focus page.
4. Maintley Intelligence is not yet the guidance layer for the Dashboard overview.

## Key Findings

### 1. Remove or Replace Home Health Score

Current implementation:

* The Dashboard displays `Home Health Score`.
* The score is calculated as `100 - 5 points per overdue task`.
* Supporting text includes score drivers such as overdue penalty and completion momentum.

Why this is a mismatch:

* Maintley Intelligence documentation says the goal is not to score properties.
* UX language guidance explicitly replaces `Home Health` and `Property Health` with `Maintley Intelligence`.
* The score is not generated by the Maintley Intelligence engine.
* The scoring formula lives in the Dashboard, which makes the Dashboard own business logic it should not own.

Recommendation:

Remove the score card in its current form.

Preferred replacement:

* A compact `Maintley Intelligence` card.
* Show one explainable suggestion derived from the shared intelligence engine or a dashboard/portfolio consumer.
* Use language like:

```text
Maintley found one thing worth reviewing across your properties.
```

Do not use:

```text
Home Health Score
Property Health
At Risk
Overdue penalty
Documentation score
```

### 2. Move Recent Maintenance Activity Lower or Remove It

Current implementation:

* Recent Maintenance Activity appears directly after the top cards and before the Needing Attention queue.
* It shows the five most recent maintenance history entries across active properties.

Why this is a mismatch:

* The Dashboard should answer: "What needs my attention right now?"
* Recent activity answers: "What happened recently?"
* That is useful context, but it is not usually the next action.
* On mobile, placing history above the action queue increases scrolling before the user reaches work they may need to complete.

Recommendation:

Move Recent Maintenance Activity below:

1. Today's Focus
2. Needing Attention
3. Maintley Intelligence suggestion
4. Seasonal Maintenance, if retained
5. Recent Maintenance Activity

Alternative:

Remove it from the Dashboard and rely on property-level Maintenance History for recent record review.

Preferred approach:

Keep it, but move it to the bottom and make it quieter. It helps reinforce Maintley's "property memory" promise, but it should not compete with action-oriented content.

Suggested label:

```text
Recent Maintenance
```

Suggested supporting copy:

```text
Recently recorded work across the properties in view.
```

### 3. Make the Dashboard Personal First, Portfolio Aware Second

Current implementation:

* Tasks are already role-filtered.
* Team-scoped accounts see tasks through `filterTasksByRole`.
* The page subtitle and overview cards still speak in portfolio-wide language.

Why this matters:

Maintley supports different user types:

* Homeowners need a personal maintenance dashboard.
* Account owners and property managers need portfolio visibility.
* Team members need assigned work and assigned property context.
* Tenants are already routed away from the Dashboard.

The Dashboard should adapt its framing to the user.

Recommendation:

Use a personal-first Dashboard model:

* For account owners and property managers:
  * Show portfolio-wide priorities across visible properties.
  * Keep property filtering.
  * Include one portfolio-level Maintley Intelligence suggestion.

* For maintenance leads:
  * Show team-visible priorities and overdue work.
  * Keep broader property context if their role supports it.

* For maintenance team members, contractors, leasing, accounting, and property guests:
  * Lead with assigned or relevant work.
  * Avoid portfolio language unless the user truly has portfolio responsibility.
  * Use labels such as `Your Focus`, `Your Tasks`, and `Properties in View`.

Suggested header copy by context:

Owner / manager:

```text
See today's priorities, recommendations, and recent maintenance across the properties in view.
```

Team member:

```text
See the work and property updates most relevant to you.
```

Single-property homeowner:

```text
See today's maintenance priorities and recommendations for this property.
```

### 4. Add a Dashboard Maintley Intelligence Consumer

The Dashboard should not create separate recommendation logic.

Recommendation:

Create a dashboard or portfolio Dashboard consumer in the intelligence layer when implementation begins.

Suggested file:

```text
src/intelligence/consumers/portfolioDashboard.ts
```

Purpose:

* Evaluate the visible dashboard property set.
* Reuse the shared Maintley Intelligence engine.
* Aggregate property-level findings into one small Dashboard suggestion.
* Respect plan and capability filtering.
* Return presentation-ready guidance without owning UI rendering.

The consumer should consider only properties visible to the current Dashboard scope:

* Hidden-from-dashboard properties excluded.
* Property filter respected.
* Role/property assignment visibility respected.

The Dashboard should consume the result and render one concise recommendation.

### 5. Reorder the Dashboard Around Action

Recommended v1 layout:

1. Personal focus card
   * "Today's Focus" or "Your Focus"
   * One highest-priority task or next action.

2. Needing Attention
   * Overdue and due-soon tasks.
   * This should move above Recent Maintenance Activity.

3. Maintley Intelligence
   * One suggestion from the dashboard/portfolio consumer.
   * Link to the relevant property, task list, systems view, or future recommendations surface.

4. Overview
   * Keep a compact property/system/task summary.
   * Avoid score or grade framing.

5. Seasonal Maintenance
   * Keep if it produces actionable task creation.
   * Otherwise consider placing below primary action sections.

6. Recent Maintenance
   * Bottom placement.
   * Optional, quiet, and history-oriented.

## Proposed Dashboard Model

The Dashboard should answer:

```text
What needs my attention right now?
```

For each user, that means:

* What should I do first?
* What work is overdue or due soon?
* What did Maintley notice that would help next?
* What property context do I need to act?

The Dashboard should not primarily answer:

* How healthy is my portfolio?
* What is my score?
* What happened recently?
* How complete are my records?

Those belong to Maintley Intelligence, Maintenance History, reporting, or future audit surfaces.

## Recommended Implementation Phases

### Phase 1 - Low-Risk Dashboard Cleanup

Goal:

Bring the Dashboard closer to current UX direction without changing data models.

Changes:

* Remove or replace the Home Health Score card.
* Move Recent Maintenance Activity below Needing Attention.
* Update the Dashboard subtitle to avoid `portfolio health`.
* Rename or soften risk-heavy language in the task queue.
* Keep all data derivation client-side and current behavior intact.

### Phase 2 - Personal Dashboard Framing

Goal:

Make the Dashboard adapt to the current user's responsibility.

Changes:

* Determine dashboard mode from role/account context:
  * owner/manager
  * maintenance lead
  * assigned team member
  * single-property homeowner
* Adjust card labels and helper text by mode.
* Keep the same underlying filters.
* Avoid exposing portfolio language to users who only need assigned work.

### Phase 3 - Maintley Intelligence Dashboard Consumer

Goal:

Add one small Maintley Intelligence suggestion to the Dashboard.

Changes:

* Add a pure consumer under `src/intelligence/consumers/`.
* Reuse the shared engine and existing prioritization/filtering.
* Aggregate findings across visible properties.
* Return one compact suggestion.
* Render the suggestion in the Dashboard overview area.

### Phase 4 - Documentation Alignment

Goal:

Keep docs and implementation aligned after code changes.

Changes:

* Update Product Direction if the Dashboard becomes explicitly personal-first.
* Update UX Language Guide with preferred Dashboard labels.
* Update Maintley Intelligence docs when the dashboard consumer is implemented.
* Consider an ADR only if the Dashboard strategy becomes a formal product architecture decision.

## Recommendation

Proceed with a Dashboard redesign in this order:

1. Remove the Home Health Score concept.
2. Move Recent Maintenance Activity to the bottom.
3. Reframe the Dashboard as personal-first.
4. Add one Maintley Intelligence suggestion through a new consumer.

This keeps the Dashboard aligned with Maintley's long-term architecture:

```text
Properties
    -> Maintenance Events
    -> Maintley Intelligence
    -> User Action
```

It also preserves the useful parts of the current implementation while removing the parts that are drifting toward scores, health labels, and reporting-style content.
